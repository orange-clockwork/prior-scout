# Prior-Scout

**既存の成果を探す。根拠を確かめてから伝える。**

Prior-Scout は、指示だけで構成された小さな Agent Skill です。要件、URL、
読み取り可能な文書をもとに、公開情報から類似するツール、サービス、Skill、
ライブラリ、研究実装を探し、根拠のある共通点と重要な違いを簡潔に示します。
既存の成果を確認する手順と調査範囲を定め、確認後は元の作業に戻ります。

**状態：`0.1.1-experimental`、ローカルのリリース候補。** 公開リポジトリや
リリースはまだ確認されていません。実際の資料読み取りを伴うスモークテストと、
新しい子コンテキストで実施した14ケースのサブエージェント監査がありますが、
下記の制約があります。用途を絞ったワークフローのパッケージであり、適切な
通常の Codex プロンプトや他の Skill より高精度だと実証したものではありません。

保守の基準は英語版 README です。各翻訳は、技術的な主張と制約を英語版に合わせます。

## 主な機能

- 目的、機能、手法、関連する同義語から検索する。
- 信頼できる資料を読み、資料の実在と、主張を裏付ける根拠の有無を区別する。
- ホスト型サービス、インストール可能なアプリ、Skill、SDK、論文、デモを区別する。
- 機能が属する成果物、バージョン、サービスプランを確認する。
- 確認できた事実を残し、不明点を明示し、所定の調査上限で停止する。
- 比較後、ユーザーがすでに許可した元の作業に戻る。

新規性、法的な位置付け、研究価値、事業性、採用すべき製品は判断しません。
改善案の提示、候補の実行、別の方向への追加調査も自動では行いません。
画像の逆検索、楽曲認識、ファイルの重複排除、網羅的な文献レビューは対象外です。

## 実行環境の要件

ホスト側に Agent Skills の読み込み、検索、資料読み取りの機能が必要です。
入力文書は、その環境で読める状態にしてください。Prior-Scout 自体には検索
エンジン、パーサー、実行時依存パッケージ、アカウント、有料 API 連携、
テレメトリーはありません。資料やツールを利用できない場合は、確認したふりを
せず、その制約を明示する方針です。

## ローカルインストール

確認に使用した [Skills CLI](https://github.com/vercel-labs/skills) 1.7.4 には
Node.js 22.20 以降が必要です。新しい対象プロジェクトからローカルの候補を
指定します。次の例は両ディレクトリが同じ親ディレクトリにある場合です。
配置に合わせて相対パスを変更してください。

```sh
npx skills@1.7.4 add ../Prior-Scout-Public-Prep --list
npx skills@1.7.4 add ../Prior-Scout-Public-Prep --skill prior-scout -a codex --copy -y
npx skills@1.7.4 list -a codex
```

コピー前に、同名の Skill が対象プロジェクトへ導入済みでないか確認してください。
既定はプロジェクト単位です。この手順にグローバル指定を追加しないでください。
配置先は `.agents/skills/prior-scout/` です。インストールされるのは
`skills/prior-scout/` のみで、同梱の LICENSE もコピーされます。
中核となる指示の管理元は一つです。

M4 では、既存の公式 CLI エントリーポイントを使用し、ローカルでの検出、
プロジェクト単位のインストール、バイト単位の一致を確認しました。
新しい Codex セッションでの動作は未検証です。
[インストール記録](evals/runs/install-m4-20261022.md)では、CLI の確認と、
npx の起動、ホストでの読み込み、リモートからのインストールを区別しています。
一つの成功から他の成功を推定しないでください。新しい Codex セッションで
登録項目を確認し、`$prior-scout` を指定して、実際の指示と資料の読み取りを
確認してください。一覧が更新されない場合はホストを再起動します。
指示ファイルを読んだ記録だけでは、別途の構造化されたローダーの動作記録にはなりません。

## 使い方

明示的な指定（この実験版では推奨）：

> $prior-scout を使って、Markdown ナレッジベースのリンク切れ、添付ファイルの
> 欠落、同名ファイルを確認できる既存のオープンソースツールを探してください。
> 信頼できる資料を読み、確認できた共通点と重要な制約を説明してください。

ホストが Skill を選択する自然な依頼の例：

> この提案に似た既存のツールや研究実装はありますか。
> 根拠のある候補をいくつか挙げ、重要な違いを説明してください。

外部との比較が必要な新規計画にも適しています。一方、通常のバグ修正、整形、
要約、翻訳、リファクタリング、実装方針が確定した作業では調査を始めるべきでは
ありません。「提供した資料だけを使う」という制限を優先します。
回答言語はユーザーに合わせます。これらは入力例であり、自動選択の成功記録ではありません。

## Evidence-First の確認方針と制約

既定の上限は検索クエリ6件、異なる外部根拠文書8件で、通常は3～5候補を示します。
これは指示上の上限であり、プログラムによる強制ではありません。検索スニペットは
手がかりにすぎず、重要な主張には資料の読み取り成功と直接の裏付けが必要です。
予定機能や連携用 API を完成済みのワークフローとは扱いません。
部分的な類似は完全な代替を意味せず、一度の検索で見つからなくても不存在とは断定しません。

回答前に、裏付けのない主張を修正し、未確認と明示するか、削除します。
全候補への二つの資料、数値スコア、長いチェックリストは要求しません。
網羅的な発見や、モデルのハルシネーションの完全な排除は保証できません。

## テストと結果

リリース監査では、品質タスク8件と Skill 選択に関する対照ケース6件の計14ケースを実施しました。
その範囲では、重要な裏付けのない主張や捏造はレビューで見つかりませんでしたが、
正答率を測ったものではありません。新しい子コンテキストを使う一方、ホストの
指示は共有され、モデルに最初に見えたプロンプト全体も記録されていません。
指示ファイルの使用が観察されても、トップレベルのネイティブ自動選択を証明する
ものではなく、構造化された読み込みの確認は未確定です。独立した A/B/C 比較、
開発に使っていない評価ケースによる検証、他ホストでの信頼性、発見した候補の
実際の動作、正確な費用、通常のプロンプトに対する品質優位性は未検証です。
