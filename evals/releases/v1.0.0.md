## Method

The existing 20-case development prompts and pinned fixtures were extended,
not replaced with an easier suite. A separately generated final 8-case packet
was frozen after RC1; its designer did not inspect old tests, outcomes or the
candidate. Grading criteria, candidate bytes and task inputs were kept out of
executor contexts except the assigned task materials and actual Skill.
Task-supplied coding tests were visible as legitimate existing project artifacts;
the grading rubric/reference judgments were not supplied to executors.

Each execution used a new ephemeral native session, isolated Git root and
runtime home. Memory, unrelated Skills, apps/plugins/hooks and non-required MCP
servers were disabled process-locally; global instructions and author history
were absent from inspected model-visible contexts. The baseline had no enabled
Prior-Scout. The substantive task and source files match between arms; only an
explicit request to use the installed Skill is removed for baseline cases.
Implicit-positive and negative prompts do not name or force-load the Skill.
Case pairs alternate which arm executes first. All final tasks receive identical
explicit source budgets and tool instructions. After observed429 errors,
cross-stage inference was serialized; interrupted attempts remain preserved.

PASS requires actual observable criterion satisfaction, not a nonempty final,
self-reported invocation, URL, HTTP200 or tool success. Selection is checked by
catalog plus actual complete-body acquisition. Source claims are checked against
content acquired in that execution. Grading is non-blind, agent-assisted evidence
review with coordinator adjudication; unsupported positive opinions do not override
source/tool facts. It is not an external human audit. Purposive cases and small
samples do not support population accuracy, causal improvement or statistical
superiority. Repeated safety/trigger trials are not new independent task types.

## Acquisition, fallback and scope

Four distinct live tasks covered software projects, browser SQLite libraries,
public Agent Skills and original publications. Their retained primary content,
failed attempts and claim-specific support were reviewed. Synthetic archived
empty/HTTP200-error fixtures are labeled as such; they do not substitute for
the live-source group. A separate real 404 plus author-published fallback was
actually exercised. 403 responses, unsupported PDFs/oversize bodies, missing
text, truncation and rereads remain visible; inaccessible content is not counted
as reviewed evidence. Batched and failed queries count separately from calls.
Budgets are instruction-level, not mechanical limits.

Authorized compare-then-recommend, plan and bounded implementation tasks were
completed. Candidate packages were not installed/executed as research objects;
coding tasks modified only their explicitly authorized synthetic project files.
Compare-only controls did not expand into adoption or unrelated research.

## Historical and intermediate evidence

Results are not pooled across incompatible protocols or revisions. Published
V03's original 40 first attempts are preserved: 28 PASS, 5 FAIL, 4 INCONCLUSIVE,
3 operational BLOCKED. The V03 arm was 14/20 PASS with 2 loading failures,
2 missing-body observations and2 interrupted attempts. Baseline was 14 PASS,
3 FAIL, 2 INCONCLUSIVE and 1 BLOCKED. Later operational recovery and audited-reader
rows are separate records, not rewritten successes. Uncommunicated original
baseline budgets were not retroactively treated as violations.

RC0's supplied-material controls also exposed observable loading misses;
RC1's description clarification was based on exposed development failures.
The older intermediate held-out packet is diagnostic, not a final RC1 score;
some operational-recovery prompts retained an English suffix and are not a
language-matched comparison. The final 8-case packet above was independently
created and separately frozen; no tuning followed its outcomes.

Existing Promptfoo, V03/V04 and Snyk reports were reviewed without rerunning
unchanged scans. The earlier V03/V04 comparisons showed no V04 advantage.
The historical Snyk 0.6.9 result reported only third_party_content_exposure
100/1000 (Low). It is not a new scan of v1.0, a zero-risk claim or an exploit
probability. The workflow/security body is unchanged, so a repeat scan solely
to seek a different score was not justified.
